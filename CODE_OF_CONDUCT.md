 # Code of Conduct
Zeta is an engineering project built around the pursuit of a fast, safe, and practical systems programming language.

To combat these AI usage policies, you can always ask:
- How the code works,
- how would you write a specific concept and lay it out in the Zeta compiler,
- where the implementation of X resides,
- and other similar questions.

To maintainers and contributors, you should:
- welcome others and be inclusive
- validate and appreciate the skills and accomplishments of one another
- help another accomplish another's goals, accepting constructive criticisms

**The rule is simple: AI may help us reason about code, but all code contributed to the canonical Zeta codebase must be written by humans with no exceptions made.**

# AI Policy

Contributors are responsible for everything they submit. They must understand the problem, make the relevant engineering decisions, write the implementation, and verify its correctness.

AI is a tool for research, analysis, and reasoning, not a substitute for engineering judgment, and generating code that happens to compile does not demonstrate that its author understands the implementation.

This policy is not an attempt to prohibit AI from software development altogether. It establishes a clear boundary between using AI to improve one's engineering and delegating the engineering itself.

## Permitted Uses of AI

AI tools may be used for the following purposes:

- **Research:** Investigating algorithms, compiler architectures, programming language design, memory models, optimization techniques, relevant literature, and existing implementations.
- **Review:** Reviewing the human-written code for any errors, soundness issues or bugs.
- **Analysis:** Examining existing code, identifying potential bugs, investigating performance bottlenecks, finding overlooked edge cases, and questioning existing assumptions.
- **Design discussions:** Exploring architectural alternatives, discussing algorithms, evaluating trade-offs, and examining the implications of different design decisions.
- **Code review assistance:** Asking AI to analyze human-written code, identify potential problems, challenge assumptions, and suggest areas requiring further investigation.
- **Optimization research:** Investigating possible macro optimizations, hot-path improvements, vectorization opportunities, and alternative algorithms.
- **Explanations:** Understanding unfamiliar concepts, interpreting errors, studying existing implementations, and learning about relevant technical subjects.

While it is encouraged to not rely as much on AI (meaning, if you don't need AI and could instead ask someone who's experienced in the Zeta programming language implementation, it's preferable to do so), it is completely allowed to use AI on the zeta programming languages while following the former conditions. 

AI suggestions are not authoritative, and the responsibility for all engineering decisions remains with the contributor.

## Absolute Prohibition on LLM-Generated Code

**No LLM-generated code may be contributed to the canonical Zeta codebase and exceptions will not be made.**

All implementation code must be authored by humans, including code that is repetitive, mechanical, trivial, or otherwise straightforward to generate automatically.

The prohibition includes, but is not limited to:

- Compiler, standard-library, runtime, and tooling implementations.
- Build scripts, development scripts, configuration code, and automation.
- Boilerplate, repetitive implementations, generated match arms, and mechanical refactors.
- Optimizations, regardless of their measured performance improvement.
- Small ergonomic improvements and isolated helper functions.
- Code produced by AI autocomplete, inline suggestions, chat-based code editing, coding agents, or other LLM-powered development tools.
- Code generated by an LLM and subsequently edited, cleaned up, reformatted, or partially rewritten by a human.
- Code generated outside the repository and later copied, adapted, translated, or otherwise incorporated into it.

An exception can be given to tests and benchmarks of any sort if you follow the following conditions:
- The first pass can be AI-generated (and subsequent regenerations if the tests/benchmarks are completely of low quality) with human corrections afterwards only.
- AI-generated tests and benchmarks (and all tests and benchmarks generally) should come from necessity (such as a new feature, a bug fix with the test proving it's okay, a regression or an unprotected invariant)

**The size, complexity, quality, and usefulness of the generated code do not affect this rule.**

A contributor must not use AI-generated code as an implementation template and then reproduce it manually to circumvent the prohibition. Human authorship requires the contributor to independently develop and write the implementation, not merely transcribe or disguise a generated solution.

AI-assisted research and high-level design discussions remain permitted. The resulting implementation, however, must be independently designed and written by the contributor rather than derived from an AI-generated implementation.

### Disclosure does not create an exception

AI-generated code cannot be made acceptable by disclosing its origin, adding a comment, requesting additional review, providing tests, or demonstrating that it works.

The prohibition is absolute. Disclosure is not a substitute for compliance.

Mechanical transformations may still be performed with conventional, non-LLM tools, including deterministic scripts and refactoring utilities, provided the process does not use LLM-generated code to produce the contribution. Contributors remain responsible for reviewing the resulting changes.

This restriction concerns LLM-generated code; it does not prohibit ordinary non-LLM code generation mechanisms used by the project, such as compiler-generated output, macros, conventional parser generators or IDE-enhanced suggestions.

## Complex Features Must Be Human-Engineered

All code must be human-written (except for tests and benchmarks with the specified conditions), but features requiring substantial engineering judgment warrant particular care.

This includes borrow checking, type checking, memory safety, ownership and destruction semantics, compiler intermediate representations, code generation, concurrency, asynchronous execution, effect systems, compile-time evaluation, and other components that materially affect language semantics, correctness, or architecture.

AI may help investigate the relevant concepts, explain existing implementations, identify possible edge cases, or challenge a proposed design. It must not supply the implementation, whether as a complete solution or as a sequence of smaller code suggestions.

The contributor must make the important design decisions, reason about the required invariants, and implement the solution independently.

Passing tests alone does not establish that a complex compiler feature is correct. Contributors must understand the relevant semantics, failure cases, and interactions with the rest of the compiler.

## Documentation Must Be Human-Written

**Using AI to write, generate, rewrite, expand, or polish Zeta's documentation is prohibited.**

This includes README files, guides, tutorials, specifications, design documents, architectural documentation, API documentation, docstrings, explanatory source-code comments, examples intended to teach the language, changelogs, and release notes.

AI may be used to research a subject or explain a concept to a contributor. The contributor must write the actual documentation themselves, based on their own understanding.

Documentation communicates the language's behavior, design, and guarantees. Its accuracy and quality require genuine understanding of the subject being documented.

AI generation of comments (including TODO comments) are also not allowed.

This prohibition is separate from the code-generation rule and must be followed independently.

## Isolated Experiments

Experiments that are AI-assisted (or even vibe coded) are permitted outside the canonical Zeta codebase. Contributors may use AI freely to create isolated prototypes, temporary repositories, or experimental forks to investigate an idea, and if applicable, rewrite it by hand in the future and contribute it to the Zeta compiler.

These experiments must remain strictly isolated from the production project under the following conditions:
- Experimental code must not be copied, cherry-picked, ported, vendored, or otherwise incorporated into the canonical codebase.
- It must not become part of the canonical compiler's build, dependencies, tests, release artifacts, or production workflow.
- Contributors must not submit pull requests to clean up, repair, improve, complete, integrate, or contribute a vibe-coded prototype to be used in production.
- Contributors must not use a prototype as the implementation foundation for a sequence of human-written or AI-assisted pull requests.

Prototype tests may not be ported to the zeta compiler, while prototype *benchmarks* can be ported with the following conditions:
- Only the workload and a harness that drives the canonical implementation through its normal interfaces may be ported. No prototype implementation code, prototype-only hooks, or production changes made to accommodate the benchmark can be ported if they were AI-generated.
- It should undergo through human review, disclosure, a real necessity, and the author able to explain what it measures.
- The benchmarked workload must not be shaped around the prototype (falsifying the benchmark to make the prototype look good) but must be representative (meaning, the workload must resemble what real users and/or the compiler will actually face)

Especially breaking the last one can lead to an immediate termination in future contributions.

**An experimental prototype may investigate or motivate an idea, but it must never become an unofficial first implementation of a production feature.**

Learning something from an experiment is permitted. Reusing its implementation, translating its code into another form, or treating it as the starting point for a production PR is not.

If an experiment reveals a promising approach, the production implementation must be independently designed and written without using the prototype's source code as its implementation foundation.

This exception exists to permit experimentation, not to provide a pathway for AI-generated implementations to enter Zeta indirectly.

## Pull Requests

Every pull request must represent work that the contributor understands and has independently implemented.

Pull requests may be rejected when they:

- Contain LLM-generated implementation code, regardless of the amount or quality of that code. (except for tests and benchmarks with the specified conditions)
- Use AI autocomplete or other LLM-powered tools to produce submitted code.
- Incorporate or derive implementation code from vibe-coded prototypes.
- Delegate complex engineering decisions to AI.
- Introduce unnecessary abstractions, excessive complexity, or unrelated changes.
- Contain unverified correctness or performance claims.
- Lack adequate tests, measurements, or reasoning for the changes being proposed.
- Include AI-generated or AI-rewritten repository documentation.

PRs with AI generated PR descriptions or commits will also be rejected.

Contributors should be prepared to explain the problem being solved, the reasoning behind their implementation, the assumptions it relies on, the relevant alternatives, and how its correctness was established.

Performance-sensitive changes should include reproducible measurements where practical. Changes involving compiler correctness, memory safety, or concurrency should include appropriate tests and reasoning about the invariants they must preserve.

A useful result does not override the code-generation prohibition. Even a correct implementation that produces a substantial performance improvement must be human-written.

## Issues and Bug Reports
Issues must describe real, sufficiently understood problems or clearly identified proposals.

Bug reports should provide reproducible behavior, expected and actual results, relevant environment information, and a minimal example where appropriate.

Feature requests should explain the problem they aim to solve and why it matters, rather than merely proposing a solution without establishing a need.

Do not submit speculative or invented bug reports, duplicate feature requests, or bulk-generated issues without independently verifying their relevance.

AI-generated issue descriptions are not allowed.

Contributors must understand the claims they make and be prepared to explain the evidence supporting them. AI may assist with research and investigation, but it does not replace evidence, reproducibility, or the contributor's understanding of the issue.

## Verification and Accountability
AI output must never be treated as an authoritative source of correctness, because it can misunderstand language semantics, invent APIs or research findings, miss subtle aliasing problems, and recommend optimizations that make real workloads slower.

Contributors must verify technical claims against the implementation, reliable documentation, primary sources, tests, and measurements as appropriate.

In Zeta, particular care is required around memory safety, aliasing, initialization, destruction, concurrency, compiler transformations, and generated machine code. A locally plausible change can violate an invariant elsewhere in the compiler or runtime.

For performance work, benchmark relevant workloads rather than relying on an AI's prediction. For correctness-sensitive work, tests should be complemented by reasoning about the relevant invariants and failure cases.

Every contributor is responsible for their submissions, regardless of how they investigated the problem or where they obtained their technical knowledge.

Repeatedly submitting prohibited code or attempting to circumvent the prohibition through incremental changes may result in restrictions on further contributions.

As well as deliberately lying about the origin of code (where it originated from AI and not a human) which will result in immediate termination from being able to contribute forever.

Additionally, requests to weaken this AI policy to be able to create slop PRs is prone to immediate rejection, not requiring further reasoning on why we rejected it.

*P.S this does not mean we won't take your feedback into consideration if you suggest a proper reasoning for weakening the AI policy, but some stuff will never be allowed. e.g. completely vibe coding a massive feature pull-request.*
